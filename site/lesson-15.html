HTTP: bản tin, phiên, cache và HTTPS

HTTP là giao thức yêu cầu–phản hồi. Cùng một tài nguyên web có thể được truyền bằng HTTP/1.1, HTTP/2 hay HTTP/3; ý nghĩa method, status và header vẫn là nền tảng để đọc luồng giao tiếp.

1. Request và response

GET /articles/7 HTTP/1.1
Host: example.org
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2

{}

Dòng đầu request gồm method, request target, phiên bản; response có phiên bản, status code, reason phrase trong HTTP/1.1. Dòng trống kết thúc header; body nếu có theo sau. Content-Length tính theo byte, không phải ký tự.

MethodÝ nghĩa thường dùng
GET / HEADLấy biểu diễn tài nguyên / chỉ lấy header.
POSTGửi dữ liệu để server xử lý; ý nghĩa do endpoint định nghĩa.
PUT / PATCHThay thế toàn bộ / sửa một phần tài nguyên theo API.
DELETE / OPTIONSXóa tài nguyên / hỏi khả năng giao tiếp, thường dùng trong CORS preflight.

GET, HEAD, OPTIONS là safe theo ngữ nghĩa chuẩn; PUT và DELETE idempotent nếu áp dụng đúng, tức lặp lại có tác dụng cuối như một lần. POST thường không idempotent. Server phải tự thực thi đúng ý nghĩa, tên method không tự bảo vệ dữ liệu.

Status: 1xx thông tin tạm; 2xx thành công (200 OK, 201 Created, 204 No Content); 3xx chuyển hướng (301/302/307/308); 4xx lỗi phía request (400, 401, 403, 404, 429); 5xx server lỗi (500, 502, 503). 401 thường yêu cầu xác thực, 403 là từ chối quyền.

Host chọn virtual host trên cùng IP; Content-Type nêu loại body; Content-Length nêu số byte; Transfer-Encoding: chunked của HTTP/1.1 cho phép gửi body theo khối khi chưa biết trước độ dài. Connection điều khiển tùy chọn kết nối theo hop trong HTTP/1.1.

2. HTTP/1.1, HTTP/2 và HTTP/3

HTTP/1.1 mặc định giữ persistent connection để tránh bắt tay TCP cho mỗi request. Pipelining cho phép gửi nhiều request trước khi nhận response, nhưng response phải trả theo thứ tự nên request chậm chặn response sau; hỗ trợ thực tế hạn chế. HTTP/2 dùng binary framing, nhiều stream multiplex trên một kết nối TCP và HPACK để nén header. Server push từng được định nghĩa, nhưng hỗ trợ thực tế đã giảm. Mất gói TCP vẫn có thể chặn byte của tất cả stream HTTP/2 trên kết nối ấy.

HTTP/3 ánh xạ HTTP lên QUIC/UDP, có stream độc lập ở tầng transport và TLS 1.3 tích hợp. Nó giảm head-of-line blocking giữa các stream khi mất gói; không làm mạng hết mất gói. Phiên bản có thể được thương lượng qua ALPN và tín hiệu hỗ trợ từ server.

3. Đăng nhập và xác thực

HTTP stateless, nên ứng dụng gắn danh tính vào từng request. Server gửi Set-Cookie: sid=...; Secure; HttpOnly; SameSite=Lax; trình duyệt gửi lại Cookie đúng phạm vi domain/path. Secure chỉ gửi qua HTTPS; HttpOnly chặn JavaScript đọc cookie; SameSite hạn chế gửi trong ngữ cảnh cross-site, giúp giảm CSRF nhưng không thay cho kiểm soát toàn diện. Session ID trỏ tới trạng thái phía server; Bearer token được gửi trong Authorization, ai cầm token hợp lệ có thể sử dụng nó. JWT là một định dạng token có chữ ký hoặc mã hóa tùy loại; chữ ký không che nội dung payload.

Basic gửi thông tin đăng nhập mã hóa Base64, chỉ an toàn khi đi trong TLS và vẫn nên cân nhắc cách quản lý mật khẩu. Digest dùng challenge/response, ít dùng trong ứng dụng web mới. Bearer đưa token vào request. OAuth 2.0 là khung ủy quyền cho client truy cập tài nguyên; OpenID Connect bổ sung lớp xác thực danh tính. Chúng không phải cùng một thứ với cookie, nhưng ứng dụng có thể dùng OAuth/OIDC để đăng nhập rồi tạo cookie phiên riêng.

4. Cache và HTTPS

Cache-Control: max-age=60 cho phép dùng response còn mới trong khoảng 60 giây tùy ngữ cảnh và directive khác. ETag là định danh phiên bản biểu diễn; client gửi If-None-Match, server trả 304 Not Modified nếu bản cũ còn hợp lệ, tiết kiệm body. Dữ liệu cá nhân cần chỉ thị cache phù hợp, ví dụ private hoặc no-store theo nhu cầu.

HTTPS là HTTP qua TLS. Trình duyệt kiểm chứng chứng chỉ gắn tên miền với khóa công khai; TLS mã hóa và kiểm tra toàn vẹn lưu lượng. HSTS bảo trình duyệt ưu tiên HTTPS trong thời gian chỉ định và giúp tránh lần truy cập HTTP sau đó; cấu hình sai có thể khiến site không truy cập được cho tới khi TLS sửa xong.

Ví dụ conditional GET: Lần đầu server trả 200 và ETag: "v3". Lần sau client gửi If-None-Match: "v3"; nếu chưa đổi, server trả 304 không body. Nếu bài viết sửa thành v4, server trả 200 kèm body và ETag mới.

5. Các thành phần web khác

Redirect trả 3xx và Location để client tới URL khác. Content negotiation dùng header như Accept, Accept-Language để chọn biểu diễn. CORS là chính sách trình duyệt kiểm soát JavaScript đọc response cross-origin; không phải cơ chế xác thực server. Forward proxy đại diện client đi ra; reverse proxy đứng trước server, có thể kết thúc TLS và cân bằng tải.

WebSocket bắt đầu bằng HTTP Upgrade (trong HTTP/1.1) rồi trở thành kênh hai chiều. SSE là luồng server→client dùng HTTP response. gRPC thường chạy trên HTTP/2, trao đổi thông điệp Protocol Buffers và hỗ trợ streaming. Chọn theo chiều giao tiếp, hạ tầng và khả năng quan sát của hệ thống.

Bài tập: API trả dữ liệu riêng của tài khoản. Client gửi If-None-Match và server muốn trả 304. Điều kiện nào phải kiểm tra trước? Vì sao không thể chỉ so ETag của một tài khoản chung?
Xem lời giải

Server phải xác thực và kiểm tra quyền truy cập tài nguyên trước khi trả 304. ETag cần gắn với biểu diễn đúng cho người dùng/quyền hiện tại; cache dùng chung không được lộ dữ liệu cá nhân. Dùng Cache-Control phù hợp, thường private hoặc no-store nếu dữ liệu nhạy cảm.

Thực hành: Chạy curl -v https://example.org xem request/response header và TLS; thêm -I để xem header, -L để theo redirect. DevTools → Network hiển thị method, status, timing, cookie, cache và protocol. Wireshark đọc rõ HTTP plaintext; HTTPS cần khóa phiên phù hợp để giải mã nội dung, nhưng vẫn thấy IP, cổng, TLS handshake và kích thước bản ghi.

6. Theo một lần tải trang

Trình duyệt giải DNS để biết IP, mở TCP rồi bắt tay TLS (hoặc QUIC cho HTTP/3), gửi GET tài liệu HTML. Server có thể trả redirect; trình duyệt theo Location rồi tải CSS, JavaScript, hình và API. Một số tài nguyên lấy từ cache; khi stale, trình duyệt có thể gửi conditional request với ETag. Một trang vì vậy có nhiều request với method, status, host và protocol khác nhau.

Khi request bị chậm, chia thời gian thành DNS, connect, TLS, chờ byte đầu tiên (TTFB) và tải body. TTFB lớn có thể do server xử lý chậm hoặc mạng trễ; chỉ một con số không xác định nguyên nhân. Kiểm tra response headers, kích thước body và waterfall trước khi tối ưu.
